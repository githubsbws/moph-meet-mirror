MOPH Meet Lite

A lightweight, stateless telemedicine platform for the Ministry of Public Health (MOPH), enabling video consultations between healthcare providers and patients — with zero database dependencies for the core user flow.

Node.js 20 LTS Express 4 No PostgreSQL required ProviderID OAuth2 Jitsi Meet SQLite (rooms only)

MOPH Meet Lite is a rewrite of the original core + user-app stack (TypeScript + PostgreSQL + Nuxt 3) into two lean Node.js services designed to run on a single low-cost server with minimal ops overhead:

⚙️

core-lite

REST API backend. Stateless authentication via ProviderID. Room management with SQLite. Port 3500.

🖥️

user-app-lite

Express + EJS server-side rendered UI. Session management. Proxies to core-lite for API calls. Port 3000.

🎥

Jitsi Meet

Self-hosted video conferencing at moph-meetingroom.moph.go.th. No per-minute cost.

🏗️Architecture

Browser / LINE / HIS │ ▼ nginx (moph-meet.moph.go.th :443) ├── /api/rooms ──► user-app-lite :3000 (session auth proxy) ├── /api/exam/* ──► user-app-lite :3000 (session auth proxy) ├── /api/media-upload ──► user-app-lite :3000 (multipart, 2 GB limit) ├── /api/* ──► core-lite :3500 (direct API) └── /* ──► user-app-lite :3000 (UI pages) user-app-lite :3000 ├── Session store (express-session, cookie-based) ├── EJS views: dashboard, login, meet, exam, queue └── Proxies to core-lite :3500 with Bearer token from session core-lite :3500 ├── ProviderID OAuth2 (moph.id.th → provider.id.th) ├── Token store: NodeCache (in-memory, lost on restart) ├── Room store: SQLite (disk-backed, 24h TTL) └── JWT queue tokens (jsonwebtoken, HS256) Jitsi Meet (moph-meetingroom.moph.go.th) └── Self-hosted video server (separate infrastructure)
ℹ️ All /api/exam/* and /api/rooms routes pass through user-app-lite first so the session cookie is translated to a Bearer token before reaching core-lite. Direct browser calls to core-lite are not possible from the public internet.

⚙️Core Functions

Provider (Doctor / Staff) Flow

  • ✓
    Login via ProviderID — OAuth2 through moph.id.th → provider.id.th. No username/password database required.
  • ✓
    Dashboard — Lists all active rooms owned by the logged-in provider, with calendar view of upcoming meetings.
  • ✓
    Create Meet Room — Instant video conference room for multi-party meetings. Returns a shareable join link.
  • ✓
    Create Exam Room — Telemedicine consultation room with patient queue. Only the owning doctor can admit patients.
  • ✓
    Invite Patient — Generate a named patient invite link (JWT-signed, 8h TTL) to send via LINE/SMS.
  • ✓
    Queue Management — Doctor sees live queue and calls next patient with one click.
  • ✓
    AI Summary Upload — Upload consultation recording for AI transcription and summary (poc-mophmeet-ai-summary).

Patient Flow

  • →
    Queue Waiting Room — Patient opens invite link → enters virtual waiting room. No login required.
  • →
    Live Queue Position — Polls queue status every few seconds. Shows position and total waiting.
  • →
    Auto-Admit to Jitsi — When doctor calls next, patient is redirected directly into the Jitsi video call.

Appointment System (3rd Party HIS)

  • ⚡
    Pre-create Room via API — POST /api/meet/reserved with doctor's CID to create a room in advance.
  • ⚡
    Generate Patient Link — POST /api/meet/reserved/token to generate a named patient queue link for a specific session.

🔑Key Capabilities

🔐

Zero-Password Auth

Doctors authenticate via ProviderID (national healthcare ID). No separate username/password database needed.

💾

Stateless by Design

Session tokens in NodeCache, rooms in SQLite. Restart-safe rooms. No PostgreSQL dependency for the core flow.

🔗

CID-Locked Rooms

Exam rooms are bound to the doctor's CID. Pre-created rooms (by HIS) can only be opened by the matching ProviderID login.

🎫

JWT Patient Tokens

Patients join via signed JWT links (8h TTL). No session or login required on patient side.

🏥

HIS Integration

Backward-compatible API keys for appointment systems to pre-create rooms and generate patient links.

📹

Self-Hosted Video

Jitsi Meet on government infrastructure. No per-user/per-minute video costs. HIPAA-grade isolation.

🤖

AI Summary

Post-consultation recording upload to AI transcription service. Async — does not block the consultation flow.

📱

Mobile Friendly

Server-side rendered EJS with Tailwind CSS. Works on smartphones via browser — no app install required.

🎨Design Theme

MOPH Healthcare Palette

Primary blue (#1a56db) · Teal (#0694a2) · Green (#057a55) · Dark navy (#1e2d40) · Light surface (#f3f4f6)

🌐

Bilingual UI

Thai-first interface with English labels. Date/time formatted in Thai locale (th-TH). Room names auto-generated in Thai.

⚡

Server-Side Rendering

EJS templates rendered on server. No SPA framework — fast initial load, works on low-bandwidth mobile connections in rural areas.

♿

Accessibility

Large touch targets, clear status indicators for queue position, high-contrast status badges for waiting / admitted / done states.

🔄User Flows

Flow A — Doctor-Initiated Exam (Queue)

1
Doctor logs inOpens moph-meet.moph.go.th → redirected to moph.id.th ProviderID OAuth → token issued
2
Create Exam RoomPOST /api/rooms { type:"exam" } → room created in SQLite with doctor's CID as owner
3
Invite PatientPOST /api/exam/:id/invite { patientName, cid } → returns JWT-signed queue URL → doctor sends via LINE/SMS
4
Patient joins queuePatient opens URL → waiting room page → polls GET /api/exam/:id/queue?jwt=… every 5s
5
Doctor calls nextPOST /api/exam/:id/next → patient status changes to admitted → patient page auto-redirects to Jitsi room
6
Consultation endsDoctor uploads recording → POST /api/exam/:id/submit-summary → AI transcription (async)

Flow B — Appointment System (HIS Pre-booking)

1
HIS creates roomPOST /api/meet/reserved { cid, startTime, endTime, displayName } → returns sessionID + doctor URL + default patient URL
2
HIS generates patient linkPOST /api/meet/reserved/token { sessionID, displayName, cid } → returns named patient queue URL
3
HIS sends linksDoctor URL sent to doctor via HIS portal. Patient URL sent to patient via LINE OA / SMS.
4
Appointment timeDoctor logs in via ProviderID → room is waiting on dashboard. Patient joins queue via link → Flow A steps 4–6 continue.

Flow C — Meet Room (Multi-party Conference)

1
Provider creates meet roomPOST /api/rooms { type:"meet" } → returns meetJoinUrl: /room/:id
2
Share linkProvider shares the full URL. Other authenticated providers can join directly.
3
Join JitsiBrowser opens /room/:id → user-app-lite fetches room info → renders Jitsi embed for the meeting domain.
