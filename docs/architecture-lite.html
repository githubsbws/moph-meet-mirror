MOPH-Meet Lite — Infrastructure Architecture

core-lite + user-app-lite + Jitsi Meet  ·  Nginx LB  ·  Cloudflare CDN

v1.0 March 2026

1   System Overview

core-lite Port 3500

Lightweight Express.js API server. No TypeScript build step. Handles authentication (ProviderID OAuth2), room/exam management, patient queue, JWT issuance, and guest tokens.

  • Session & token store → SQLite (better-sqlite3, disk-backed)
  • Room store → SQLite (rooms.db, lazy TTL expiry)
  • Auth → SHA-256 token + static API key whitelist
  • External deps → moph.id.th, provider.id.th

user-app-lite Port 3001

Express.js + EJS server-side rendered web app. Proxies all data through core-lite. Provides dashboards, meeting rooms (Jitsi embed), exam rooms with patient queue, and AI summary upload.

  • View engine → EJS templates (login, dashboard, meet, queue)
  • Session → express-session (in-memory, cookie 24 h)
  • File uploads → multer (memory storage, 2 GB limit)
  • Static assets → /public (CSS, JS, images)

Jitsi Meet moph-meetingroom.moph.go.th

Self-hosted Jitsi Meet platform providing WebRTC video/audio conferencing. Branded as "MOPH Meet". Embedded into user-app-lite views via JitsiMeetExternalAPI iframe. Containerized with Docker (Nginx-Alpine).

  • Frontend → Custom Jitsi Meet Web (nginx-alpine container, port 80/443)
  • Signaling → Prosody XMPP server (BOSH /http-bind + WebSocket /xmpp-websocket)
  • Media → Jitsi Videobridge (JVB) — WebRTC SFU, UDP :10000
  • NAT → TURN/STUN coturn server (ports 3478, 5349)
  • Plugins → 60+ custom Prosody modules (lobby, polls, breakout rooms, etc.)
  • Assets → CSS, fonts (Oleo Script), sounds, lang (50+ locales), virtual backgrounds

3   Request Flow Diagrams

3.1   Doctor Login (ProviderID OAuth2)

Doctor opens https://moph-meet.moph.go.th/login → Cloudflare → Nginx → user-app-lite serves login.ejs
Doctor clicks "Login with ProviderID" → browser redirects to moph.id.th OAuth2 authorize URL with client_id + redirect_uri
After credentials, moph.id.th redirects back to /auth/providerid/callback?code=XXXX → Cloudflare → Nginx → user-app-lite
user-app-lite calls CORE_BASE/api/auth/providerID (direct, bypassing Nginx/internet) with the OAuth code
core-lite exchanges code → moph.id.th/api/v1/token → gets HealthID access_token
core-lite exchanges HealthID token → provider.id.th/api/v1/services/token → gets Provider service token
core-lite fetches profile from provider.id.th/api/v1/services/profile
core-lite creates SHA-256 session token, stores user in sessions.db (SQLite), returns token + user to user-app-lite
user-app-lite saves token + user in express-session cookie, redirects doctor to / (dashboard)

3.2   Create Exam Room & Patient Invite

Doctor clicks "สร้างห้องตรวจ" on dashboard → POST /api/rooms with {"type":"exam"}
user-app-lite proxies to CORE_BASE/api/rooms with Bearer token
core-lite generates room ID (SHA-256 truncated to 12 chars), creates room object, stores in rooms.db
core-lite mints a patient JWT (8 h TTL) with roomId + role:patient, returns patientJoinUrl = /queue/:id?jwt=TOKEN
Doctor generates invite link via POST /api/exam/:id/invite with patient name → returns shareable URL
Doctor shares link (LINE, SMS, etc.) → patient opens link in browser

3.3   Patient Queue & Video Call Flow

Patient opens /queue/:id?jwt=TOKEN → Cloudflare → Nginx → user-app-lite
user-app-lite verifies JWT via POST CORE_BASE/api/jwt/verify, renders queue.ejs waiting room
Patient's browser polls GET /api/exam/:id/queue?jwt=TOKEN every few seconds → proxied to core-lite
Patient is auto-registered in room queue on first poll (status: waiting)
Doctor clicks "เรียกคนไข้ถัดไป" → POST /api/exam/:id/next → core-lite admits next patient (status: admitted)
Patient's next poll returns status: admitted → browser redirects to Jitsi Meet room (embedded iframe on MEETING_DOMAIN)
Video call runs via external Jitsi server; optional recording uploads video to AI Summary service (ABS) for transcription

3.4   Reserved Room (3rd-Party HIS Integration)

External HIS/EMR calls POST /api/meet/reserved with {startTime, endTime, cid, displayName} (no auth required)
core-lite creates exam room, mints doctor session token + patient JWT, returns {sessionID, meet: doctorURL, patientJoinUrl}
HIS sends meet URL to doctor app, patientJoinUrl to patient via SMS/LINE
Doctor opens URL with ?token= → auto-session created via autoSessionFromToken middleware → enters exam room
HIS can also call POST /api/meet/reserved/token to generate additional patient invite links

Pain Points & Opportunities

🔴 ProviderID OAuth ช้า

Token exchange ผ่าน moph.id.th → provider.id.th ใช้เวลา 3-8 วินาที อาจ timeout ถ้า network ช้า

🔴 Polling ทำให้รอนาน

คนไข้ต้อง poll ทุก 3-5 วินาที ทำให้มี delay ไม่เกิน 5 วิ ก่อนรู้ว่าถูกเรียก เสี่ยงปิดหน้าจอระหว่างรอ

🔴 ไม่มีแจ้งเตือน Push

ถ้าคนไข้ปิด browser หรือ lock จอมือถือ จะไม่ได้รับการแจ้งเตือนเมื่อถึงคิว

🔴 ลิงก์หมดอายุ 8 ชม.

JWT มี TTL 8 ชม. ถ้านัดล่วงหน้าข้ามวัน ลิงก์จะหมดอายุก่อนวันนัด

💡 WebSocket / SSE แทน Polling

ลด latency เรียกคนไข้เหลือ < 1 วินาที ลด network traffic 90%

💡 Web Push Notification

แจ้งเตือนคนไข้แม้ปิดหน้าจอ ใช้ Service Worker + pwa-worker.js ที่มีอยู่แล้ว

💡 QR Code Inline

แสดง QR ในหน้าแพทย์ให้คนไข้สแกนเลย ไม่ต้องส่ง link ทาง LINE/SMS

💡 Appointment-Based Token TTL

ผูก JWT expiry กับเวลานัดหมาย (startTime) แทนค่า 8 ชม. คงที่

Key Nginx Headers

  • X-Real-IP — real client IP (from Cloudflare)
  • X-Forwarded-For — proxy chain
  • X-Forwarded-Proto — original protocol (https)
  • Host — original host header

Recommended Additional Directives

  • client_max_body_size 2g; — support video uploads via multer
  • proxy_read_timeout 300s; — long-running AI summary requests
  • proxy_buffering off; — for real-time queue polling
  • set_real_ip_from 173.245.48.0/20; ... — Cloudflare IP ranges for $remote_addr

8   Limitations & Constraints

🔴 Critical Limitations

!
Single Server / No Horizontal Scaling — Both services run on one VM. SQLite (file-locked) prevents multi-instance deployment. A single server failure takes down the entire system. No auto-scaling under load spikes.
!
In-Memory Sessions (user-app-lite) — express-session uses the default MemoryStore. Server restart loses all user sessions (doctors must re-login). Not suitable for clustered/PM2-cluster mode.
!
SQLite Write Contention — Under heavy concurrent writes (many rooms created simultaneously), SQLite's single-writer lock can become a bottleneck, causing SQLITE_BUSY errors.
!
Open API Endpoints — /api/meet/reserved, /api/meet/reserved/token, and /api/guest/token have no authentication. Any client can create rooms and mint patient tokens. Must add IP whitelist or API key gating.
!
TLS Verification Disabled — NODE_TLS_REJECT_UNAUTHORIZED=0 is set globally in core-lite, and user-app-lite uses an insecure HTTPS agent. Vulnerable to MITM attacks on outbound calls to government APIs.

🟠 Operational Limitations

⚠
No Database Backup / Replication — SQLite files (sessions.db, rooms.db) are the only data stores. No automated backup. Disk corruption = total data loss.
⚠
Polling-Based Queue — Patient queue uses HTTP polling (client-side setInterval). Each patient generates ~10-20 requests/minute. With 100 patients waiting, this creates ~1,000-2,000 req/min of polling traffic.
⚠
24-Hour Room TTL — All rooms auto-expire after 24 hours (lazy purge). No persistent history, audit trail, or meeting records beyond the TTL window.
⚠
No Rate Limiting at App Level — No Express rate-limiter middleware. Must rely entirely on Cloudflare + Nginx for rate limiting. Internal calls (server-to-server) bypass these protections.
⚠
Video Upload Size (2 GB) — multer's memory storage holds the entire video in RAM before forwarding. A 2 GB upload can spike memory usage significantly. Concurrent uploads may cause OOM.
⚠
No Health Check Orchestration — No PM2, systemd watchdog, or container orchestration (K8s). If Node.js crashes, manual intervention is required to restart.

🔵 Design Limitations

ℹ
No WebSocket / SSE — Real-time updates (queue status, room events) require polling. Adds latency (poll interval) and unnecessary network traffic.
ℹ
SSR Only (EJS) — No SPA framework, no client-side routing. Every navigation is a full page reload. Limited interactivity compared to Vue/React SPA.
ℹ
Hardcoded API Keys — Static API key whitelist in auth.js middleware. No rotation mechanism, no per-client scoping.
ℹ
No Logging / Monitoring Stack — Only console.log output. No structured logging (JSON), no log aggregation, no APM, no alerting.
ℹ
Single JWT Secret — One JWT_SECRET for all patient tokens. Key compromise = all patient tokens forgeable. No key rotation support.

⚠ หมายเหตุสำคัญสำหรับ ISP

  • SNI-based filtering: แนะนำ whitelist ด้วย SNI (domain) ไม่ใช่ IP เพราะ Cloudflare IP เปลี่ยนได้
  • UDP port 10000: จำเป็นสำหรับ WebRTC media — ถ้า block จะ fallback TCP แต่คุณภาพ video ลดลง
  • TURN (3478/5349): จำเป็นสำหรับ user ที่อยู่หลัง strict NAT/firewall (เช่น Wi-Fi โรงพยาบาล)
  • ไม่ต้อง whitelist port 3001, 3500: เป็น internal port ที่ bind localhost เท่านั้น ไม่ expose internet
  • Data cap suggestion: แนะนำ toll-free cap ~5 GB/session สำหรับ fair use (video call ~2 ชม.)
